简化版方案（我建议）
形态
做一个桌面 App（Windows/Linux）
不依赖浏览器页面，不走 WebSocket 复杂实时链路
只做 4 个按钮：开始录音、停止、本地列表、上传
本地只存音频文件（是的，可行）
文件格式：wav（先不压缩，稳定）
目录结构（示例）：
recordings/YYYY-MM-DD/*.wav
recordings/manifest.json（记录每个文件上传状态）
manifest.json 字段最小化：
id
file_name
created_at
duration_sec
status (pending/success/failed)
retry_count
last_error
这样不用先上 SQLite，复杂度最低，出问题也容易人工排查。

上传策略（最简）
App 启动时检测网络
有网就扫 pending/failed 文件逐个上传
上传成功改 success
失败记录错误，下次再试
支持手动“全部重传”
服务端对接（尽量复用现有）
你现在已有登录和上传接口，客户端只需要：

登录拿 token
调上传接口传文件
回填结果到 manifest.json
如果现有上传接口依赖会话状态，就加一个简单新接口（单文件上传即可）。

技术实现建议（同样走简化）
首选：Python + PySide6（开发快、跨平台、打包简单）
录音：sounddevice + soundfile
HTTP：requests
打包：Windows 用 PyInstaller，Linux 也可一套打包脚本

1) manifest.json 确定版（最小可用）
{
  "version": 1,
  "device_id": "WIN-ABC123",
  "updated_at": "2026-04-23T10:00:00Z",
  "items": [
    {
      "id": "rec_20260423_095001_a1b2c3",
      "file_name": "2026-04-23/rec_20260423_095001_a1b2c3.wav",
      "created_at": "2026-04-23T09:50:01Z",
      "duration_sec": 32.4,
      "sample_rate": 16000,
      "channels": 1,
      "status": "pending",
      "retry_count": 0,
      "last_error": "",
      "uploaded_at": "",
      "server_bucket": "",
      "server_key": ""
    }
  ]
}
状态枚举：

pending：待上传
uploading：上传中（进程崩溃后可回退成 pending）
success：已上传
failed：上传失败，等待重试

3) MVP 功能清单（3~5天可落地）
Day 1
录音开始/停止（保存 wav）
生成 id 和相对路径
写入 manifest.json（pending）
Day 2
本地列表页面（按时间倒序）
显示状态/时长/错误
支持删除未上传音频
Day 3
登录（账号密码 -> token）
单文件上传
成功回填 success 和服务端返回信息
Day 4
批量上传（pending + failed）
重试策略（手动重试 + 启动时自动重试一次）
失败错误写入 last_error
Day 5
打包脚本（Windows/Linux）
基础日志与异常兜底
小范围验收
4) 验收标准（最小）
断网可连续录音并保存本地
联网后一键上传全部待传文件
失败任务可重试，且状态清晰
重启 App 不丢数据（manifest 与文件一致）
